# PostPipeline

## Описание проекта

**PostPipeline** — асинхронный конвейер обработки данных на Python, предназначенный для получения, анализа и сохранения публикаций с использованием нескольких моделей параллелизма.

Проект демонстрирует совместное применение `asyncio`, `multiprocessing` и `threading` для решения разных типов задач: сетевого ввода-вывода, вычислительной обработки данных и записи результатов в файл.

В качестве источника данных используется API [JSONPlaceholder](https://jsonplaceholder.typicode.com/).

## Основные возможности

- Асинхронное получение 100 публикаций через HTTP API.
- Ограничение количества одновременных запросов до 5.
- Параллельный анализ публикаций с использованием нескольких процессов.
- Вычисление SHA-256 для текстового содержимого публикаций.
- Расчёт показателя сложности текста.
- Мониторинг прогресса обработки в отдельном процессе.
- Передача сообщений между процессами через `multiprocessing.Queue`.
- Использование общего счётчика и блокировки для безопасного обновления состояния.
- Многопоточное сохранение результатов.
- Синхронизация доступа к файлу при параллельной записи.
- Логирование событий и ошибок.

## Архитектура проекта

Конвейер разделён на несколько этапов. Каждый этап отвечает за отдельную задачу и использует подходящий механизм конкурентного выполнения.

### 1. Получение данных — `fetcher.py`

Модуль отвечает за получение публикаций из JSONPlaceholder.

Для сетевых запросов используется асинхронное выполнение с помощью `asyncio`. Такой подход позволяет ожидать ответы сервера, не блокируя выполнение программы на время сетевого ввода-вывода.

Основные задачи модуля:

- Получение публикаций через HTTP API.
- Асинхронное выполнение запросов.
- Ограничение количества одновременно выполняемых запросов до пяти.
- Сбор полученных данных для последующей обработки.
- Обработка ошибок, возникающих при обращении к API.

Асинхронная модель особенно полезна для сетевых операций, поскольку большая часть времени может уходить на ожидание ответа сервера.

### 2. Анализ данных — `analyzer.py`

Модуль отвечает за обработку полученных публикаций.

Для вычислительной части используется `multiprocessing`, позволяющий распределять работу между отдельными процессами. Это помогает задействовать несколько ядер процессора для подходящих CPU-bound задач.

В процессе анализа выполняются следующие операции:

- Обработка содержимого публикации.
- Вычисление SHA-256 с помощью модуля `hashlib`.
- Расчёт показателя сложности текста.
- Подготовка результатов для дальнейшего сохранения.

Использование отдельных процессов позволяет изолировать вычислительную работу от основного потока выполнения и распределять независимые задачи между рабочими процессами.

### 3. Мониторинг обработки

Для отслеживания прогресса используется отдельный процесс мониторинга.

Обмен информацией между рабочими процессами и монитором организуется с помощью механизмов межпроцессного взаимодействия.

В частности, могут использоваться:

- `multiprocessing.Queue` — передача сообщений о ходе обработки.
- `multiprocessing.Value` — хранение общего счётчика обработанных элементов.
- `multiprocessing.Lock` — синхронизация доступа к общему счётчику.

Блокировка предотвращает одновременное изменение общего значения несколькими процессами в критической секции.

Мониторинг позволяет отслеживать состояние конвейера и получать информацию о количестве обработанных публикаций.

### 4. Сохранение результатов — `saver.py`

Модуль отвечает за запись результатов анализа в выходной файл.

Для организации сохранения используется многопоточность с помощью `threading`. Результаты могут распределяться между рабочими потоками через очередь.

Основные задачи модуля:

- Приём результатов анализа.
- Передача результатов рабочим потокам через очередь.
- Сохранение данных в выходной файл.
- Синхронизация параллельного доступа к файлу с помощью блокировки.
- Координация завершения работы потоков.
- Обработка ошибок записи.

Поскольку операции ввода-вывода часто связаны с ожиданием, многопоточность позволяет организовать работу нескольких исполнителей без необходимости создавать отдельный процесс для каждого сохранения.

Блокировка файла необходима для предотвращения конфликтов при одновременной записи нескольких потоков.

### 5. Координация конвейера — `main.py`

Главный модуль отвечает за запуск и координацию этапов обработки.

Он связывает получение данных, анализ и сохранение результатов в единый рабочий процесс.

Общая последовательность работы:

1. Получение публикаций из API.
2. Передача публикаций на параллельный анализ.
3. Отслеживание прогресса обработки.
4. Передача результатов в подсистему сохранения.
5. Запись обработанных данных в выходной файл.
6. Завершение работы исполнителей и освобождение ресурсов.

## Architecture Choices — архитектурные решения

### Почему используется asyncio?

Получение публикаций связано с сетевым вводом-выводом. Асинхронный подход позволяет выполнять несколько запросов конкурентно, не блокируя поток на время ожидания ответа сервера.

Ограничение числа одновременных запросов помогает контролировать нагрузку на API.

### Почему используется multiprocessing?

Анализ данных может включать вычислительные операции. Отдельные процессы позволяют выполнять такие задачи параллельно и использовать несколько ядер процессора.

Межпроцессное взаимодействие и синхронизация позволяют передавать результаты и отслеживать прогресс выполнения.

### Почему используется threading?

Сохранение результатов связано с файловым вводом-выводом. Несколько потоков позволяют организовать конкурентную обработку заданий на запись.

Очередь упрощает передачу результатов рабочим потокам, а блокировка защищает общий файл от конфликтующих операций записи.

### Почему этапы разделены на отдельные модули?

Разделение обязанностей упрощает сопровождение проекта:

- `fetcher.py` отвечает за получение данных.
- `analyzer.py` отвечает за вычислительную обработку.
- `saver.py` отвечает за сохранение результатов.
- `main.py` координирует работу компонентов.

Такую архитектуру проще тестировать, изменять и расширять: реализацию одного этапа можно улучшать независимо от остальных, сохраняя общий интерфейс взаимодействия.

## Обработка ошибок и синхронизация

При работе с сетью, процессами и файлами возможны различные ошибки. Поэтому необходимо учитывать сбои HTTP-запросов, исключения при анализе и ошибки записи результатов.

Для координации конкурентного выполнения используются очереди, счётчики, блокировки и другие подходящие средства синхронизации.

При завершении работы важно корректно останавливать рабочие процессы и потоки, дожидаться завершения задач и освобождать занятые ресурсы.

## Результаты работы

Результаты анализа сохраняются в выходной файл, путь и формат которого определяются реализацией `saver.py`.

Во время выполнения также могут создаваться журналы событий. Их назначение — облегчить диагностику ошибок и наблюдение за ходом обработки.

В репозитории не следует хранить временные файлы, журналы выполнения и кэш Python, если они не нужны для самого проекта.
